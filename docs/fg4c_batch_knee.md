# FG-4c — 批量拐点测量：GPU 批量值不值得做、在哪个 B 上做

**一句话结论：不值得做（在今天的 N 与现实的 B 下）。** 拐点确实存在且可测，
但在生产规模 N=230 上它落在 **B*=16**，而 RL 在线路径的真实批宽是 **B=1**；
同一套数学的 **纯 CPU 批量化在 B=4 就已经越过拐点**，且不需要 GPU。
本 WP 只做测量，未实现生产 GPU 路径。

所有数字由 `scripts/fg4c_render_doc.py` 从 `results/fg4c_batch_knee.json` 直接渲染，未经手工转录；
复算命令见 §8。

## 0. 口径

- **测的是完整单跨段核**（RK4/SRS ODE + 张量化 NLI + ASE），不是 GEMV。
- **同进程交错** CPU/GPU，每轮翻转顺序，取 **min 样本**（FG-4a/FG-4b 口径）。
- 设备：Tesla P100-PCIE-12GB，torch 2.14.0+cu126，CUDA 12.6。
- `loadavg` 前后各记一次，随每行报出；GPU 利用率与显存逐点记录。
- 显存用量有界：进程被限制在 50% VRAM，实测峰值 1571 MiB / 12288 MiB，**未 pin 满卡**。

### 0.1 线程钉死（这不是洁癖，是可测量的）

本机 20 核，且**同时有别人的任务**（brief 已知；本轮实测 `loadavg` 10.0–25.3）。
**前两次整轮扫描都因为 BLAS 线程超订而作废**，症状是同一个 N 下「CPU 每候选耗时」本应与 B 无关，却随 B 抖动 20 倍：

| N=900 的 CPU 每候选 | B=1 | B=4 | B=16 | B=64 |
| --- | --- | --- | --- | --- |
| 未钉线程（作废轮） | 26.5 ms | 255 ms | 551 ms | 469 ms |
| `OMP_NUM_THREADS=8`（采用轮） | 14.9 ms | 15.3 ms | 15.1 ms | 15.2 ms |

钉死之后每候选耗时在全部 B 上**持平**（N=230：1034/959/953/956/958/962 µs，N=900：14.9/15.3/15.1/15.2/15.2/16.2 ms，N=2100：145.0/145.9/149.3/147.3/149.1 ms），这正是「测到了工作量本身而不是测到了机器忙闲」的判据。**采用轮全部在 `OMP_NUM_THREADS=8 OPENBLAS_NUM_THREADS=8 MKL_NUM_THREADS=8` 下测得。**

这条对结论方向的影响已核对：钉线程会让 CPU 变慢，即让 GPU 显得更好，因此「GPU 划算」一侧的读数是**偏乐观**的；而 N=230 的关键读数（B=1 时 GPU 慢 2.9×）与低负载未钉线程轮次（GPU 2907 µs vs CPU 977 µs）**独立吻合**，结论不依赖线程设定。

### 批量形态为什么是 3 个 GEMM 而不是 (B,N,N) 张量

朴素的批量 XPM 会物化一个 `(B,N,N)` 张量：N=2100、B=1024 时是 **36 GB**，
不可能装下。把扰动轴 `l` 上的求和按 `ratio` 的幂次归并后，它塌缩成三个
`(N,N)@(N,B)` 矩阵乘，工作内存降到 O(B·N) + O(N²)：

```
u0 = p_sq * big_t^2 / rs ;  u1 = u0*ratio ;  u2 = u0*ratio^2
M0 = (gamma_sq*w0*(1-eye))^T ; M1 = ... ; M2 = ...   # 对角置零 = 排除自配对
sigma_xpm[b,i] = (32/27)*p_in[b,i] * (u0@M0 + 2*(u1@M1) + u2@M2)
```

**这一步是本 WP 唯一的结构性发现，也是批量值得被测的前提。**

## 3. 拐点（F4c-1 / 问题 1）

**B\*** = GPU 每候选耗时首次低于 CPU 逐候选每候选耗时的 B。

| N | B\*（GPU 越过 CPU 逐候选） | 首次胜出幅度 | 最优 GPU/CPU | CPU 批量越过 CPU 的 B | 最优 GPU/CPU批量 |
| --- | --- | --- | --- | --- | --- |
| 230 | 16 | 3.83x | 38.2x | 4 | 4.56x |
| 900 | 1 | 2.17x | 145.8x | 1 | 12.31x |
| 2100 | 1 | 6.85x | 372.6x | 1 | 148.92x |

三个 N 的拐点都**存在**，但位置随 N 显著左移（见问题 2）。

## 4. 问题 2：S+C+L+U 是否改变结论

**改变，而且方向对 GPU 不利——拐点左移。**

- **N=230**：B\* = 16。B=1 时 GPU 每候选 3,035 us vs CPU 1,034 us——**GPU 慢 2.93×**；要到 B=16 才转为 3.83× 胜出。
- **N=900**：**B\* = 1**——最小的 B 上 GPU 就已经快了 2.17×，不存在拐点右移的空间；全程占优，最优 145.8×（B=1 时 GPU 6,864 us vs CPU 14,865 us）。
- **N=2100**：**B\* = 1**——最小的 B 上 GPU 就已经快了 6.85×，不存在拐点右移的空间；全程占优，最优 372.6×（B=1 时 GPU 21,160 us vs CPU 145,033 us）。

机理是两条，方向相反但都指向「大 N 更适合 GPU」：

1. **启动开销被摊薄得更彻底。** RK4 是 20 步 × 4 子步 = **80 次** `(N,N)@(N,B)`，外加 XPM 的 3 次。B=1 时这 83 次小 GEMM 全部是启动开销（N=230 实测 2.9 ms/候选，几乎全部是 launch latency）；B 变大后同样的 launch 数摊到更多候选上。
2. **CPU 侧的 (N,N) 访存随 N² 涨，GPU 侧算力随 N²·B 涨且有 83 次并行流。** N=230→2100 时 CPU 每候选涨约 140×，而 GPU 在 B=1 上只涨 7×。

**但「拐点左移」不等于「该做」**——生产规模是 N=230，不是 N=2100。

## 5. 问题 3：RL 是否真有这么宽的 batch（关键）

**并行维度真实存在，但真实批宽远低于 B\*。**

### 5.1 这个 batch 维确实存在

`scan.py:552-572` 的 `verify_for_scan` 对每个候选做：

```python
temp_profile = link_state.launch_power_profile_w.copy()
temp_profile[channel_idx] = launch_power_w      # 每个候选改的是**不同信道**
temp_noise[link_key] = self._calc_link_noise(plan, temp_power_profiles[link_key])
```

每个候选在**同一条链路、同一组跨段**上换掉一个信道后重算一次完整跨段核。
所以「同一跨段上同时评估 B 个候选配置」不是假设，**它就是 `env.py` /
`scan_prune` / `feasibility` 的实际调用形态**。本 WP 的批量核正是按这个形态建的
（同一基线占用谱 + 每个候选抬高一个信道，候选信道在带内均匀铺开）。

### 5.2 但现实 B 是多少

| 位置 | 批宽 | 说明 |
| --- | --- | --- |
| `learn/hier.py:500` `retry_m: int = 1` | B = 1 | 分层策略的有界重试列表；**默认就是一个信道**（docstring 明说 m=1 与 `channel=k` 逐位相同） |
| `env.py:407` `_try_first_fit` | B = 1..频段大小 | 沿空闲信道扫描，**第一个可行就 return**（早退） |
| `env.py:485` `_try_first_fit_candidates` | B = retry_m | 按策略偏好序逐条试，同样早退；全不过才判阻塞 |
| `reopt/trial.py:205` `trial_move` | B = 1 | 每个 (业务, 候选信道) 一次试算 |
| `scan_prune.py:311` `top_k` | B = k | 策略侧截断；k ≥ 空闲信道数时与全量枚举逐位一致 |
| `feasibility.py:212` / `policies/search.py:66` | B = 88 (C) / 142 (L) | **离线**全量枚举；**不是**在线 RL step |

频段信道数取自 `bands.py`（C+L 栅格 230 道）与 `scan.py` 开头的剖析：
**C = 88 道、L = 142 道**。

**在线 RL step 的真实 B 是 1。** 依据有三条，且互相独立：

1. `learn/hier.py:500` `retry_m: int = 1`——策略侧的有界重试列表默认长度就是 1，
   其 docstring 明说「`m = 1` 时列表长度为 1，env 侧的语义与 `channel=k` 逐位相同」。
2. `env.py:407` `_try_first_fit` 在**第一个可行信道就 return**；
   `_try_first_fit_candidates` 同样逐条试、全不过才判阻塞。两者都是早退语义。
3. `reopt/trial.py` 每次 `trial_move` 只试一个 (业务, 信道)。

只有 **离线** 全量枚举（`feasibility.py`、`policies/search.py`、速率表构建）
才真的把一个频段的 88/142 条信道全试一遍。

### 5.3 结论：GPU 不划算

在生产规模 N=230、**现实批宽 B=1** 下，GPU 每候选 3,035 us，CPU 逐候选 1,034 us——**GPU 慢 2.93×**。
这不是「赢得不多」，是**输**。而 B=1 正是 RL 在线路径的形态。

CPU 批量的结论是**划算但要在 B≥4 才划算**：N=230 时 CPU 批量每候选 660 us （B=4，vs 逐候选 959 us），到 B=1024 为 115 us。**但 B=1 的在线路径同样吃不到**——B=1 时 CPU 批量反而比逐候选慢（1,967 us vs 1,034 us，多出来的正是把 B=1 也走成 GEMM 的开销）。

**所以两条路都救不了 B=1。** 真正能吃到批量的是离线全量枚举（B=88/142），
而那已经在离线路径上、且不占 RL step 的延迟预算。

## 6. 问题 4：端到端投影

投影口径：一次真实 QoT 评估 = **跨段数 × 单跨段核**。
下面按每候选调用物理内核的次数给出「今天 → 批量后」。

| 场景 | B | 跨段数 | 口径 | 今天（CPU 逐候选） | 批量后 | 倍数 |
| --- | --- | --- | --- | --- | --- | --- |
| N=230 在线 step（`_try_first_fit`） | 1 | 3 | 现实批宽 | 3.1 ms | GPU 9.1 ms / CPU批量 5.9 ms | GPU 0.34× / CPU 0.53× |
| N=230 离线全量枚举（band C，实测 B=64） | 64 | 3 | B 实测 | 183.6 ms | GPU 22.0 ms / CPU批量 31.4 ms | GPU 8.34× / CPU 5.84× |
| N=230 离线全量枚举（band L，实测 B=256） | 256 | 3 | B 实测 | 735.5 ms | GPU 29.6 ms / CPU批量 90.8 ms | GPU 24.88× / CPU 8.10× |
| N=900 离线全量枚举（实测 B=256） | 256 | 3 | 假设性 N | 11,701.5 ms | GPU 108.1 ms / CPU批量 665.3 ms | GPU 108.27× / CPU 17.59× |
| N=2100 离线全量枚举（实测 B=256） | 256 | 3 | 假设性 N | 114,533.1 ms | GPU 408.2 ms / CPU批量 6,185.8 ms | GPU 280.58× / CPU 18.52× |

**所有行的 B 都是实测栅格上的点**（B ∈ {1,4,16,64,256,1024}）。
真实的频段全量批宽 C=88 / L=142 **不在栅格上**，它们落在实测的 **B=64 与 B=256 之间**；由于每候选耗时对 B 单调下降，**B=88/142 的收益落在该两行之间**——这是**区间**而非点值，本 WP **没有**为 88/142 编造读数。

**必须同时读的限制：**这里的「一次 QoT 评估」只计入**物理内核调用**。`scan.py` 开头的剖析显示，内核只占单次 `verify_allocation` 的 **33–38%**，其余是 `_build_path_snr_array`、`spectrum.frequencies` 属性重算等 Python 开销。**因此这些倍数是内核层面的上界，不是端到端 step 的加速比。**

## 7. 建议（F4c-5）

**不做生产 GPU 路径。** 理由按证据强度排序：

1. **生产规模上 GPU 在 B=1 是输的**（N=230：2.93× 慢）。而 B=1 是 RL 在线路径的真实形态（§5.2）。
2. **唯一的大 B 场景是离线全量枚举**（B=88/142），它不占 RL step 的延迟预算，收益上界是内核的 24.9× 且被 Python 开销摊薄（§6）。
3. **纯 CPU 批量化在 B≥4 就能拿到大部分收益**，且不引入 CUDA 依赖、不跨设备改数值口径。

**值得留给下一个 WP 的，是这个已测出来的事实**：N 从 230 涨到 2100 时拐点左移到 B*=1，最优点 373×。**如果 S+C+L+U 真的落到槽级（N≈900–2100），GPU 值得重新评估**——
那是一个**需求驱动的重开**，不是本轮的结论。触发条件写清楚：B 维必须同时满足
「N≥900」且「同一跨段上真实批宽 ≥16」。

**一个附带结论（不在本 WP 授权内，仅记录）**：CPU 批量核在 B≥4 时比逐候选快，
而它就是本文件 §0 的那 3 个 GEMM。若编排方要一条**不引入 GPU** 的加速，
CPU 批量化是把 §2 里那条 1.88×/4.678× 之后的剩余空间吃掉一半的现成形状。
