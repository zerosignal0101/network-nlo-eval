# FG-4d — S+C+L+U 的真实 N 与真实批宽 B，并据此裁定下一步加速

**一句话裁定：做 CPU 批量。** 本 WP 推翻 FG-4c 的两条前提假设——但**不是**推翻它的拐点曲线。

- **FG-4c 假设的 B=1 是错的。** 真实 rollout 实测 **B 均值 68.5 / 72.1**
  （400 Erl 两个样本），**中位 75.5 / 88.0**，**p95 ≈ 141**（= band L 的信道数）。
  FG-4c §5.2 从「`retry_m=1` + 早退」**推断**出 B=1——那是策略默认值，不是测量值。
  早退的真实含义是「**试到第一个可行为止**」，而在现实负载下**多数候选 QoT 不过**，
  于是要试几十条才命中。
- **FG-4c 假设的 S+C+L+U → N=900/2100 也偏高 4.4×。** 灵活栅格下真实 N ≤ **480**。
  原因与 FG-4c 的假设方向相反：**ODE 节点 = 连接数，不是带宽**。一条占 6 槽的宽连接
  只占 **1 个**节点，连接越宽 → 节点**越少**。

两条修正合在一起，把结论从「都不做」翻到「CPU 批量值得做」：
FG-4c 实测曲线上 **CPU 批量在 B≥4 越过拐点**，而真实 B=68.5 ≫ 4。

所有数字来自 `results/fg4d_rollout_400Erl.json` 与 `results/fg4d_flexgrid_n.json`；
加速倍数引用 FG-4c 的实测曲线（`results/fg4c_batch_knee.json`），未外推。复算命令见 §7。

## 1. 未知量 1：ODE 的真实节点数 N（F4d-1）

### 1.1 先说结构性事实：N 由「连接数」驱动，不由「带宽」驱动

ODE 节点数就是物理内核入参的长度 `N = len(power_in_w)`，实测 319,027 次内核调用
**全部 N=230**（100%）。但这里有**两种模式**，本 WP 的第一个发现就是把它们分开：

| 模式 | 进入方式 | N 等于 | 与负载的关系 |
| --- | --- | --- | --- |
| **A：当前生产实现** | RL 仓走 `SpectrumGrid`（`connections=None`） | **栅格宽度** = `num_channels` = 230 | **无关**。未占用信道以 0 功率参与 ODE，仍是一个节点 |
| **B：FG-D 逐连接模式** | `MultiBandISRSGN(..., connections=[ConnectionSpec...])` | **活跃连接数** | **随连接数长** |

模式 A 的依据是硬契约，不是推测：`isrs_gn.py:368` 要求
`power_in_w.shape == (n_nodes,)`，而 `n_nodes = f_abs_hz.shape[0] = grid.frequencies.shape[0]`
（遗留模式 `isrs_gn.py:181`）。`launch_power_profile_w` 也是按 `num_channels` 开的零数组
（`network/state.py:122`）。**所以今天 C+L 上 N 恒为 230，哪怕一条连接都没有。**

模式 B 才是 FG-D 设计的「每连接一个节点」：节点频率取 `ConnectionSpec.centre_hz`。

### 1.2 三档频段的真实 N（模式 B，灵活栅格 12.5 GHz 槽）

现实业务取 RL 仓 `request.py::DEFAULT_BITRATE_SNR` 的阶梯
（100G-QPSK / 200G-QPSK / 300G-16QAM / 400G-64QAM），
槽宽由 `slots_for_rate` 强制，得 **4 / 8 / 6 / 6 槽**（均值 **6.0 槽/连接**）。

| 频段档 | 槽数 | 总宽 | 等效 50 GHz 道数 | N @25% | N @50% | N @75% | **N @100%（满载）** |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **C+L** | 916 | 11.45 THz | 229 | 38 | 76 | 115 | **153** |
| **S+C+L** | 1667 | 20.84 THz | 416 | 70 | 139 | 208 | **278** |
| **S+C+L+U** | 2877 | 35.96 THz | 719 | 120 | 240 | 360 | **480** |

**N 的驱动量是连接数**，读法：`N = 槽数 ÷ 6.0`。同一份带宽，用**更宽**的连接铺 →
连接更少 → **N 更小**。这就是 FG-4c 的 N=900/2100 偏高的原因：它按
「50/25 GHz 固定栅格铺满」折算，等价于假设**每连接只占 1 道**；而现实需求平均占 6 槽。

**U 段来源已标注**：本仓与 RL 仓**均无 U 段定义**，此处按 ITU-T U 波段 1660–1770 nm
以 c 精确换算（169.3733–180.5983 THz）。这是本 WP 的假设，不是既有资产。

### 1.3 N 的实测内核代价（模式 B，OMP 钉 8 线程）

| N | 单次跨段核耗时（中位） | 备注 |
| --- | --- | --- |
| 153 | 0.484 ms | C+L 满载 |
| 230 | 1.143 ms | **生产 N**，与 §3 的 1.178 ms 独立互证 |
| 278 | 1.853 ms | S+C+L 满载 |
| 480 | 8.072 ms | S+C+L+U 满载 |
| 900 | 25.611 ms | FG-4c 的「GPU 触发线」，灵活栅格**达不到** |

`loadavg` 5.0–5.1。

## 2. 未知量 2：真实批宽 B（F4d-2）

### 2.1 测法

B = **一次枚举决策内候选评估的次数** = 相邻两次 `env.step` 之间的
`verify_for_scan` 调用数（`_try_first_fit` 在该决策内逐条试、第一个可行就 return）。
探针在运行时包住 `ScanValidator.verify_for_scan` 计数，**不改动 RL 仓任何文件**。

### 2.2 实测分布

两个独立样本（400 Erl，stage-4 的留出评测工况）：

| 统计量 | 30 决策样本 | **50 决策样本** |
| --- | --- | --- |
| 均值 | 68.5 | **72.1** |
| 中位 | 75.5 | **88.0** |
| p25 | 1.0 | — |
| p75 | 136.5 | — |
| p90 / p95 | 139.2 / 141.6 | — / **140.6** |
| p99 | 142.0 | — |
| min / max | 1 / 142 | 1 / 142 |
| P(B≥4) | **0.633** | — |
| P(B≥16) | **0.633** | — |
| 阻塞率 | 0.300 | 0.280 |
| `loadavg`(1m) | 20.2 | 5.1 |

30 决策样本的完整直方图是**双峰**的：
`{B=1: 10 次, B=2: 1, B=44…60: 4, B=91…102: 5, B=135…142: 9}`。
`max=142` 正是 **band L 的信道数**——即「整段频段全试完仍不可行」。

**读法**：B=1 的那 10 次是**早退立刻命中**；其余 63% 的决策把整个频段的空闲信道
**几乎试穿**才判阻塞。现实负载下 QoT 才是筛子（带宽筛子只挡「已占用」），
所以候选评估次数**远大于**策略默认的 `retry_m`。

**这直接推翻 FG-4c §5.2/§5.3 的「在线 step 真实 B 是 1」。** 那条结论由三条「依据」支撑
（`retry_m=1`、`_try_first_fit` 早退、`trial_move` 单点），三条都只说明了**上限与语义**，
没有一条测量过**实际命中前的候选数**。早退 ≠ B=1。

## 3. step 级成本分解（快速通道口径，F4d-3）

**不再引用 `verify_allocation` 的 33–38%**（编排方已纠正该推论：快速通道 `scan.py`
本身就是逐位等价通道，33–38% 是**慢通道**的剖析，对本口径无效）。

快速通道口径下 `step 成本 ≈ 内核调用次数 × 单次内核成本`，两个因子都实测：

| 量 | 实测值 | 来源 |
| --- | --- | --- |
| 内核调用 / 候选评估 | **155.3** | 319,027 / 2,054 |
| 候选评估 / step（即 B） | **68.5** | 2,054 / 30 |
| 内核调用 / step | **10,634** | 319,027 / 30 |
| 单次内核成本 | **1.178 ms** | 375.79 s / 319,027 |
| **内核占 step wall** | **98.9%** | 375.79 s / 379.97 s |

单次 step = 12.53 s，其中内核 12.39 s，**非内核仅 1.1%**。

**⇒ 快速通道上已经几乎没有 Python 开销可捡。** 编排方纠正的方向是对的，且比纠正更强：
不是「还有 62–67% 可捡」，而是**剩下 1.1%**。唯一的杠杆是**把内核调用本身批量化**。

**交叉互证**：§1.3 用模式 B 独立测得 N=230 时单次核 **1.143 ms**，与本节
rollout 内的 1.178 ms 相差 3%（后者含 monkeypatch 计时开销且负载更高）——两条独立路径
落在同一量级，N=230 的单次核代价可信。

## 4. 裁定（F4d-4）

三选一，理由逐条挂实测数字：

### ✅ 选 **CPU 批量**（B≥4 时赢）

1. **FG-4c 的 CPU 批量拐点是 B≥4**（`fg4c_batch_knee.md` §3，N=230 行）。
   实测 **B 均值 68.5 / 72.1**（两个样本）、**P(B≥4)=0.633**
   ⇒ 触发条件**大幅满足**（拐点的 17–18 倍）。
2. **收益可观且超过已兑现的存量**：按实测 B=72 与 N=230，
   step 级 **12.53 s → ~1.7 s ≈ 7.2×**。
   用 FG-4c 自己的读数（serial 956.4 µs/cand，钉线程+低负载，更保守）
   则为 **5.85×**。两者都**高于** FG-4a+4b 累计的 **4.678×**。
3. **不动物理、不动 API、不引 CUDA**；数值口径与现在逐位同源（同一批 GEMM 改写）。

### ❌ 不选 **GPU**（条件「N≥900 且 B≥16」只满足一半）

1. **B≥16 满足**（68.5 ≫ 16）。
2. **但 N≥900 不满足，且达不到**：生产 N=**230**（实测，100% 调用）；
   灵活栅格三档满载也只有 **153 / 278 / 480**，**S+C+L+U 满载都到不了 900**。
   ⇒ FG-4c §7 自己写下的**重开条件不成立**。
3. 诚实附注：若只看 FG-4c 的 **N=230 曲线**，GPU 在 B=64 处给 **8.34×**（本 WP 投影
   **10.27×**），比 CPU 批量的 5.85×/7.20× **只多 1.43×**。为这 1.43× 引入 CUDA 与
   跨设备数值口径，**在 N=230 上不划算**。这是「不选」的理由，不是「GPU 没用」。

### ❌ 不选 **都不做**

被 1 的第 1、2 条直接否掉：真实 B=68.5 落在 CPU 批量的甜点区，
收益（5.85–7.20×）**高于**继续吃 FG-4a/b 的 4.678×。

### 一句话给编排方

> **先做 CPU 批量。** 它的触发条件（B≥4）已被实测满足且余量 17 倍，
> 收益 5.85–7.20× > 存量 4.678×，且不引 CUDA。
> **不要为此开 GPU**：FG-4c 写下的「N≥900」在灵活栅格下**永远达不到**（满载 480）。
> 若将来 N 真被推到 ≥900（B 仍 ~68），GPU 相对 CPU 批量再多 1.43×，届时再评估。

## 5. 批量化为什么成立（形态已在 FG-4c 验证）

一个决策内的 B 个候选**共享同一条路径、同一组跨段**，只差「抬高哪个信道」
（`scan.py:563-565`）。这正是 FG-4c §0.1 那 3 个 GEMM 的批量形态
（`sigma_xpm = (32/27)·p_in·(u0@M0 + 2·u1@M1 + u2@M2)`，扰动轴归并成 3 个 `(N,N)@(N,B)`）。
FG-4c 已实测该形态的数值精度（最差 1.54e-14，预算 1e-12）与批宽收益曲线。
**本 WP 不重复验证，只确认「真实 B 落在这条曲线的哪一段」。**

## 8. 未测 / 不确定（F4d-7）

1. **B 的分布只在一档负载（400 Erl）上完整采到**，且 **seed 只有 1 个**。
